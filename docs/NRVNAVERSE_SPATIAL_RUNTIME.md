## 2. Official AWE runtime mount

`AweSpatialRuntime` is adapted from `examples/starter` (`game-script.ts` + `utils.ts` + `game-canvas.tsx`, plus the official `touch-joystick.tsx` / `jump-button.tsx` copied verbatim). Upstream lifecycle is preserved: `Engine.getInstance().createSpace()` → player lookup → `createInputs` / `ThirdPersonCameraRig` / `Mover` / `createMoverAnimStateMachine` → `reveal()` → `space.start()` → `dispose()`; `onFixedUpdate` drives input, mover and animation exactly as the starter does. One engine instance, one space; React Strict Mode is handled with the starter's "dispose only after load" guard.

Deliberate deviations from the starter (documented in the file header):

1. `init()` does **not** reveal. The application reveals only after the initial placement (or gate refusal) is settled, so the world is never shown at the wrong place.
2. No "click to start" screen and no pause toggle; the space starts on reveal. Pointer lock still engages on the first canvas click through the upstream Mediator; Esc releases it.
3. `placeVisitor(spawn)` — same-scene teleport through `Mover.teleport()` (official rigid-body teleport, velocity cleared) followed by `ThirdPersonCameraRig.reset()`.
4. Canvas resize also listens to a `ResizeObserver` on the container (upstream listens to `window.resize` only).
5. `tsconfig.json` adopts the starter's `strict: false` / `strictNullChecks: false` because the app now type-checks engine sources through path mapping; NRVNAVerse-owned pure modules stay strict via `tsconfig.strict.json` (run with `pnpm --filter the-nrvnaverse exec tsc --noEmit -p tsconfig.strict.json`; wiring it into the `check` script is a pending `package.json` change awaiting approval).

Assets: the 17 starter animation clips (`public/assets/anims/*.json`, text JSON, byte-identical to `examples/starter`, so Git stores no new blobs) and upstream CDN assets (VRM `sunshine.glb`, default anims, fonts, grid texture). No new binaries, no Ghost assets.

## 4. Placement registry (stable id → physical placement)

> **Superseded by M0 Step 2B.1** — see [`NRVNAVERSE_SPATIAL_DATA_PIPELINE.md`](./NRVNAVERSE_SPATIAL_DATA_PIPELINE.md). The hand-kept `placements.m0.ts` was deleted; the registry is now built at boot from the generated spatial index (`destinationId → chunkKey → spawn`), and `placementRef` is `chunk:<key>`. The rules below still hold.

`M0_PLACEMENTS: Record<destinationId, { worldId, placementRef, spawn: { position, yaw } }>` — keyed by the committed stable ids (Manifest doc §3). Rules:

- It lives in the app's spatial layer, **separate from `packages/nrvna-manifest/manifests/*.json`**. The manifests gained nothing; the validator still rejects any extra field in `spatialDestination` (tested: no `position`, `spawn`, `chunkKey`, `yaw` anywhere in the manifest data).
- Coordinates are replaceable implementation details; re-laying-out the world edits this file only. `placementRef` (e.g. `m0:music`) is a diagnostics handle, never identity and never written to a URL.
- Evolution path for Step 2B: add `chunkKey` beside `worldId` → `destinationId → chunkKey → spawn` without touching identity. A **generated** spatial index may replace the hand-kept file later; `portals-index.json` was **not** created (no technical requirement arose).
- The gated destinations **are** registered so the gate check is proven against a real placement (placement exists, travel still refused).

## 5. Adapter behaviour (`AweSpatialAdapter`, `name: "awe-spatial-adapter"`)

| Call | Behaviour |
|---|---|
| `canTravel(id)` → `TravelEligibility` | unknown id → `unknown-destination`; non-public status → `not-public`; **`gates.length > 0` → `gate-required` (evaluated before placement and before runtime readiness)**; no registry entry → `unplaced`; runtime not ready → `unavailable`; otherwise `allowed`. Never throws. |
| `resolvePlacement(id)` | registry lookup → `resolved { worldId, placementRef }` or `unplaced`. Does not move anyone; works before the runtime exists. |
| `travelTo(id)` | emits `traveling`; re-runs `canTravel`; on `allowed` calls `runtime.placeVisitor(spawn)` (same-scene teleport) and emits `arrived`; gate → emits `gateRequired` and returns `gate-required { gates }`; otherwise `failed` / `unavailable`. Records a `travel` perf measurement with the outcome. |
| `onPhase(listener)` | subscription with unsubscribe; `dispose()` clears all listeners and detaches the runtime (further travel → `unavailable`). |

The interface change in Step 2A: `SpatialTravelAdapter.canTravel` became a per-destination method returning a structured `TravelEligibility` (was a boolean property). `PlannedSpatialAdapter` remains as the honest null adapter for engine-less contexts.

Application/UI code never passes or receives a coordinate: `DirectoryNav` calls `travelToDestination(id)`; the store calls `adapter.travelTo(id)`; the UI shows `placementRef` for diagnostics only.

## 6. Gate-required placeholder behaviour

For the 21+ Cannabis District and NRVNA Farms Placeholder (manifest `gates: [{ kind: "age21", … }]`):

- `canTravel` → `gate-required`; `travelTo` → `gate-required`, **no teleport**, adapter phase `gateRequired`.
- Deep link `?destination=<cannabis-id>` → engine loads, adapter refuses, visitor is placed at the Hub, app phase `gateRequired`, URL left untouched (reload reproduces the refusal). In-app click → phase `gateRequired`, visitor stays where they are, URL unchanged.
- The manifest's placeholder `enforced: false` is deliberately **not** consulted: declaring a gate is enough to stop spatial entry. No age verification, no jurisdiction logic, no "I am 21" bypass, no gated content fetch exists in this build (Landmark §9 policy stays configurable at the application/content layer and is not implemented).

## 7. Application state and URL contract

Implemented phases: `boot`, `resolvingDestination`, `loadingGlobals`, `ready`, `traveling`, `arrived`, `gateRequired`, `error` (`IMPLEMENTED_PHASES`). Reserved, not implemented: `loadingChunk` (`PLANNED_PHASES`). Settled phases (`ready | arrived | gateRequired`) allow a new travel; `arrived`/`gateRequired` return to `ready` on dismiss. All transitions are pure functions in `app-state.ts`.

URL: on arrival the store writes `?destination=<stable-id>&from=spatial[&ref=…]` via `buildDeepLinkQuery`; failed or gated travel writes nothing; browser back/forward travels to the destination the URL names without adding history; `?chunk=` is ignored on input (Step 1 contract) and is never written (tested).

## 8. Instrumentation

`perf.ts` wraps `performance.mark/measure` (`nrvna:` prefix) and records to an in-memory list shown in the prototype "Spatial travel → performance" panel; development builds also `console.debug` each measure. Nothing is POSTed anywhere. Measured: `boot→engine-ready`, `boot→revealed` (initial destination resolve → world revealed), `travel` per attempt with `{ destinationId, outcome }` (arrived / gate-required / failed / unavailable).

Baseline on the development machine (Windows 10, Next dev server, Turbopack, warm cache, foreground tab): `boot→engine-ready` ≈ 1.9–2.1 s, `boot→revealed` ≈ 4.6–4.8 s (includes the upstream intro tunnel), same-scene `travel` ≈ 1–20 ms, gate refusal < 1 ms. First cold load was 9.3 s / 12.1 s.
